# 语宙（LinguaVerse）V1 开发计划

**版本：** 1.2
**日期：** 2026-09-06
**范围：** V1 垂直切片——语言交流体验
**引擎：** Godot 4.7.2 + Blender 4.2.8
**平台：** Godot Desktop（Linux/Windows/macOS，不发布 Web）

---

## 〇、V1 唯一目标：语言交流

> **V1 只做一件事：让人在 3D 场景里和 AI NPC 用目标语言自由对话。**
>
> 3D 场景、玩家移动、昼夜循环……这些都是为了让对话"发生"而存在的最小载体。
> 核心验证：**AI 驱动的自然语言对话，能不能成为有效的语言学习方式？**

### V1 体验闭环

```
启动应用 → 进入场景 → 靠近 NPC → NPC 主动打招呼 →
键盘输入目标语言 → AI 自然回应 → 多轮自由对话 →
对话自然结束 → 换个 NPC 继续聊
```

### V1 验证的唯一核心假设

> **在 3D 沉浸场景中，用 AI 驱动的自由对话进行语言交流，是否比传统学习方式更自然、更有效？**

其他假设（昼夜、探索欲、帧率）都是次要的，可以在 V2 验证。

**开发顺序（按优先级）：**
1. **M4 对话系统**（P0 核心）—— 先搭后端，验证 AI 对话能跑通
2. **M3 NPC 系统**（P0 核心）—— NPC 模型 + 行为 + Prompt
3. **M2 玩家系统**（P1）—— 最小可用的移动 + 靠近触发
4. **M1 3D 场景**（P1）—— 最小可用的场景（能放下 NPC 和玩家就行）
5. **M6 导出部署**（P2）—— 让别人能玩到
6. **M5 世界系统**（P3）—— 昼夜、音效（锦上添花）

**为什么对话先做？** 因为对话是唯一要验证的核心假设。场景可以很简陋，但对话必须流畅自然。

## 三、开发阶段（按优先级重排）

### Phase 1：对话系统后端（M4 核心，2-3 天）

> 目标：先让 AI 对话能跑通——这是 V1 的核心

| # | 任务 | 说明 |
|---|------|------|
| 1.1 | Node.js + Fastify 服务搭建 | 基础 HTTP 服务器 + CORS |
| 1.2 | LLM 适配器层 | 统一接口，支持 Ollama（开发）/ DeepSeek（生产） |
| 1.3 | Prompt 组装器 | NPC 身份 + 世界状态 + 对话历史 → Prompt |
| 1.4 | 对话 API | POST /api/dialog（请求-响应） |
| 1.5 | SSE 流式 API | POST /api/dialog/stream（逐字生成） |
| 1.6 | 本地 curl 测试 | 验证对话质量、响应速度、法语生成效果 |

**API 设计：**

```
POST /api/dialog
Request:  { player_input, npc_info, conversation_history, world_state }
Response: { text, npc_name }

POST /api/dialog/stream
Request:  { player_input, npc_info, conversation_history, world_state }
Response: SSE 流，每个 chunk: data: {"text": "词", "done": false}
```

**Phase 1 交付：** 一个能用 curl 测试的对话 API——输入法语，AI 用 NPC 身份自然回复。

---

### Phase 2：Godot 前端对话（M4 前端 + M2 最小移动，2-3 天）

> 目标：在 Godot 里能看到对话效果

| # | 任务 | 说明 |
|---|------|------|
| 2.1 | 台词气泡 UI | Godot Control 节点（PanelContainer + Label + 动画） |
| 2.2 | 对话输入框 | Godot LineEdit + Button 节点 |
| 2.3 | HTTPRequest 调用后端 API | 输入 → 发送到后端 → 接收回复 → 显示 |
| 2.4 | 最小玩家移动 | WASD + 鼠标（已有骨架，能走到 NPC 面前就行） |
| 2.5 | 靠近触发对话 | 走近 NPC 自动开始对话 |

**Phase 2 交付：** 在 Godot 里走到一个 NPC 面前，打字聊天，AI 回复显示在气泡里。

---

### Phase 3：NPC 系统（M3，2-3 天）

> 目标：3 个有身份的 NPC

| # | 任务 | 说明 |
|---|------|------|
| 3.1 | NPC 模型（Blender 或 CC0） | 服务员、行人、老人 |
| 3.2 | NPC 行为脚本 | idle / walk / talking 状态 |
| 3.3 | NPC Prompt 每人不同 | 身份、性格、说话方式 |
| 3.4 | NPC 招呼语 | 靠近时自动说的第一句话 |
| 3.5 | NPC 名牌 | 头顶显示名字 |

**NPC Prompt 模板：**
```
你是 {名字}，一个巴黎 {职业}。
你的性格是 {性格}。
你会说法语，但不会英语。
玩家是一个刚搬到巴黎的新居民，法语不太好。
说话要求：自然、口语化、简短。
```

**Phase 3 交付：** 3 个不同身份的 NPC，各有各的性格和说话方式。

---

### Phase 4：3D 场景（M1，3-5 天）

> 目标：对话发生的最小场景

| # | 任务 | 说明 |
|---|------|------|
| 4.1 | 咖啡馆室内（最小可用） | 柜台 + 几张桌子，能走进去就行 |
| 4.2 | 一小段街道 | 咖啡馆门口 + 几米路面 |
| 4.3 | 基础光照 | 不需要昼夜循环，固定白天就行 |

**场景可以很简陋——重点是对话体验，不是画面。** 后续再打磨场景。

**Phase 4 交付：** 一个能走进咖啡馆、走到柜台前的最小 3D 场景。

---

### Phase 5：体验打磨（M5 + M2 打磨，2-3 天）

> 目标：让对话体验更自然

| # | 任务 | 说明 |
|---|------|------|

| 5.4 | 昼夜循环（可选） | 如果时间允许 |
| 5.5 | 环境音（可选） | 如果时间允许 |

**Phase 5 交付：** 对话体验流畅自然——思考动作、自然结束、短期记忆。

---

### Phase 6：打包发布（M6，0.5 天）

> 目标：生成可执行文件

## 五、技术约束

| 约束 | 说明 | 应对 |
|------|------|------|
| Web 性能 | 桌面浏览器 30+ fps | 场景 < 30,000 面，Compatibility 渲染器 |
| 包体大小 | 首次加载可接受 | Godot 运行时 ~15MB + 资产 ~5MB |
| LLM 延迟 | NPC 回复 < 3 秒 | 思考动作 + 流式响应 |
| 浏览器兼容 | 现代浏览器 | Chrome / Firefox / Edge，WebGL 2.0 |
| 单线程 | Godot 4.3+ 默认 | 不需要 SharedArrayBuffer 头 |

## 六、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| Godot Desktop 性能不足 | 低 | 高 | Desktop 原生性能极好，风险低 |
| JavaScriptBridge 不稳定 | 低 | 高 | Godot 4.x 已稳定，官方文档确认 |
| 3D 资产制作耗时 | 高 | 中 | 优先用 CC0 资产，不追求完美 |
| LLM 响应太慢 | 中 | 中 | 思考动作掩盖延迟；流式响应 |
| 团队不熟悉 GDScript | 中 | 中 | GDScript 语法简单，1-2 天上手 |

## 八、完成标准

### 玩家体验闭环
```
启动应用 → 进入巴黎街头 → WASD 移动探索 → 走进咖啡馆 →
服务员招呼 → 键盘输入对话 → NPC 自由回应 → 咖啡端来 →
走出咖啡馆 → 继续探索 → 天色变化
```

### 技术完成标准
- 桌面浏览器稳定 30+ fps
- NPC 对话响应延迟 < 3 秒
- 昼夜循环流畅运行
- 无明显卡顿/崩溃
- Desktop 导出正常运行
