## 〇、一句话

V1 的问题不再是"没做"，而是"**做了但无法声称**"。本方案把 V1 从"文档上的完成"推到"可验证的完成"：先修两个阻断 bug，再把验证体系立起来，让每个 ✅ 都有可重算的证据。

## 一、背景与差距

### 1.1 为什么出这版方案

`docs/V1开发计划.md` 的六个 Phase 里，Phase 1–5 标为完成，但：

- 对话系统"✅ 完成"的判定依据是 headless 结构自检，**没有一次真实走完的体验闭环**；
- 两个阻断性 bug 使 V1 核心闭环目前**物理上不可完成**（按 E 开始对话后无法退出）；
- 帧率、对话延迟、画面观感**零实测数据**，全部是估算；
- 没有一键验证入口，资产再生成会直接覆盖已验收文件。

GTA_SZ 项目用"哈希绑定的验收状态机 + 四层验证防线 + 资产管线纪律"把"完成"变成可重算的机器判定，这套方法正好补本项目的短板。

### 1.2 现状（2026-10-05 源码核实）

| 模块 | 实测事实 | 差距 |
|---|---|---|
| 对话退出 | `dialog_manager.end_dialog()` **全仓库无调用方**；`player_controller.gd:25/53` 在 `is_in_dialog` 时输入与物理全部 early-return | 按 E 开始对话后玩家永久锁死（软锁），决策 9「走开自然结束」未实现 |
| ESC/暂停 | `game_manager.gd:24` 消费 ESC 调 `get_tree().paused=true`；autoload 未设 `PROCESS_MODE_ALWAYS` | 暂停后可能无法恢复，疑似第二个软锁 |
| 后端开箱 | `server.ts:13` 使用 `pino-pretty` transport，`package.json` 未声明；仓库无 lockfile | 干净安装 `node dist/server.js` 直接崩溃，"对话系统 ✅"从未在干净环境成立过 |
| Prompt | `dialog_manager.gd:72` 先 append 玩家输入，`prompt_builder.ts:75` 再 push 一次 | 每轮 user 消息重复出现两遍 |
| 超时 | `dialog_manager.gd:93` 的 `HTTPRequest` 未设 timeout；`dialog_ui.gd` 无超时态 | 后端挂起则玩家永远"思考中" |
| LLM 护栏 | 适配器直接取 `OLLAMA_MODEL`，无模型类型/输出校验 | base 模型（如 `qwen2.5-coder:7b-base`）返回垃圾文本时全盘崩坏，无重试降级 |
| 流式 | 后端 `/api/dialog/stream` 已实现，Godot 端 `append_stream_text()` 是死代码 | 首轮 6s 等待无感知，决策 6「思考动作」只有静态文案 |
| 昼夜 | `main.tscn:60` 写死 `fixed_hour=14.5` | 当前场景昼夜是锁死的演示模式 |
| 验证 | 只有 `street_check.gd`（14 项）与 `dialog_check.gd`，人工命令行触发；backend 连 `test` 脚本都没有 | 无门禁、无 CI、无回归样本、无性能采样 |
| 资产 | `cafe.glb`、`rosiers_layout.json` 无 manifest（面数/来源/SHA256） | 资产一改，旧"✅"仍留在文档里 |
| 文档漂移 | `巴黎场景搭建-实施计划.md` 写 `rosiers_raw.json`，实际是 `data/osm/rosiers_full.json` | 历史文档不改写，但要标注实际以什么为准 |

代码量对比：GDScript 1,269 行 + 后端 TS 486 行 + Python 558 行，文档 14 篇 3,460 行——**文档远多于代码，欠的是执行与验证，不是规划**。

### 1.3 借什么、不借什么

| 借（GTA_SZ 被事故打磨过的四件事） | 不借（差异与风险） |
|---|---|
| ① 哈希绑定的验收状态机（源/产物 SHA 一变旧结论失效） | ① 引擎细节（Babylon 材质/灯光 hack 与 Godot 无关，只借方法） |
| ② 四层验证防线（单测→资产校验→真机实测→具名人工复核） | ② 分块流式加载（V1 一条街，`整个巴黎-技术方案.md` 自己也说 V1 不需要） |
| ③ 资产管线纪律（增量、隔离候选、清单交叉核对、预算） | ③ "游戏不依赖 LLM"方向（本项目核心假设恰恰是 LLM，要建同等级质量验证） |
| ④ 文件所有权 + 单一集成者 + 执行止损（多会话并行时才启用） | ④ 千行 README / 三语文档负担、脚本路径硬编码 |

## 三、阶段一：P0-A 对话链路阻断修复（本轮实施）

| # | 任务 | 涉及文件 | 验收判据 |
|---|---|---|---|
| A1 | **对话退出路径**：① `dialog_manager` 每 0.5s 检测玩家与 `current_npc` 距离 >4m 或脱离视线持续 2s → 调 `end_dialog()`；② 对话中按 ESC → 调 `end_dialog()`；③ `end_dialog()` 补全链路：NPC 状态回 IDLE、UI 隐藏、玩家输入锁释放、鼠标恢复捕获 | `scripts/dialog/dialog_manager.gd`、`scripts/player/player_controller.gd`、`scripts/dialog/dialog_ui.gd` | `dialog_check.gd` 新增断言：触发→走开→`is_in_dialog=false`；ESC→结束；均通过 |
| A2 | **ESC 单一处理方**：`game_manager` 设 `PROCESS_MODE_ALWAYS`；对话中 ESC 优先结束对话不触发暂停；非对话 ESC 暂停后**再按 ESC 必须能恢复** | `scripts/autoload/game_manager.gd` | 新增断言：暂停→恢复循环两次不卡死 |
| A3 | **后端开箱即跑**：`package.json` 声明 `pino-pretty`；补 `test` 脚本；生成并入库 `pnpm-lock.yaml` | `backend/package.json`、`backend/pnpm-lock.yaml` | 干净安装 → `pnpm build` → `node dist/server.js` → `/api/health` 200 |
| A4 | **Prompt 重复修复**：契约定死「`conversation_history` = 已发生的历史；`player_input` = 当前句」。Godot 端不再提前 append 玩家输入，只在响应回来后 append user + assistant 各一条 | `scripts/dialog/dialog_manager.gd`、`backend/src/services/prompt_builder.ts` | 后端单测/断言：组装出的 messages 中同一句 user 只出现一次 |
| A5 | **超时与错误码**：`HTTPRequest.timeout = 20000`；后端错误返回稳定 code（`LLM_TIMEOUT` / `LLM_BAD_OUTPUT` / `LLM_UNAVAILABLE`），Godot 端按 code 映射友好中文，不透传底层技术错误 | `dialog_manager.gd`、`backend/src/routes/dialog.ts` | 断言：后端不启动时 UI 显示友好提示且不卡死（现有行为保持）；超时有提示 |
| A6 | **LLM 护栏**：启动时校验模型名，`base`（非 instruct）模型直接拒绝并给明确 code；输出非空 + 长度上限 + 法语特征粗检；连续 2 次失败降级返回固定安抚话术并记 code | `backend/src/services/llm_gateway.ts`、`backend/src/adapters/*.ts` | 配置 `-base` 模型时启动/首轮即被拒；垃圾输出触发降级而非透传 |

**阶段一整体不能声称：** 对话质量、延迟达标、画面表现——这些由阶段二与真机验收负责。

## 七、资产预算与哈希绑定约定

| 项 | 预算 | 超预算处理 |
|---|---|---|
| 单个 GLB | ≤ 8 MiB | 记录理由 + 实测数据，人工批准后改预算 |
| 贴图 | ≤ 2048×2048 | 同上 |
| 室内精模（咖啡馆） | ≤ 20,000 面 | 同上 |

| 验收绑定 | 结果文件内嵌被校验资产的 SHA256 | 资产变更 → 旧验收自动失效，须重跑 |

## 十、Git 与协作纪律

1. **分支：** 本次经研发确认在 `main` 直改（常规应走 feature 分支 + PR）。
2. **不自动提交：** 只有研发明确说"提交/推送"才执行，且执行前再次确认。
3. **验证手段：** 编译 + 自动化测试——`godot --headless` 结构与对话检查、`tsc --noEmit`、`tools/verify.sh`；重型导出/打包验证交 CI 或研发环境。
4. **止损规则：** 一版 + 至多两次定向修复；连续两次同类错误停下，提交问题升级说明而不是无限重试。
5. **范围纪律：** 严格按本方案任务清单实施，实施中发现范围外需求先停下确认。
