# 整个巴黎——技术方案

**日期：** 2026-09-06
**问题：** 如果要做整个巴黎（105km²、10 万+建筑），技术上怎么实现？

---

## 〇、核心矛盾

| 维度 | 小街区（500m×500m） | 整个巴黎（10km×10km） |
|------|-------------------|---------------------|
| 建筑数量 | 80 栋 | 100,000+ 栋 |
| 总面数 | 15,000 | 1,200,000+ |
| 数据大小 | 1 MB | 500MB-1GB |
| 加载方式 | 一次性加载 | **必须分块流式加载** |
| Web 可行性 | ✅ 完全可行 | ⚠️ 需要特殊架构 |

**结论：** 整个巴黎不能用"生成全部→全部加载"的方式。必须用**流式加载**。

---

## 一、方案 A：分块流式加载（Chunk Streaming）

> **核心思路：** 只加载玩家周围 200m 范围内的建筑，远处的不加载。

### 1.1 架构

```
┌─────────────────────────────────────┐
│            整个巴黎 OSM 数据          │
│         （500MB，存储在服务器）         │
└─────────────────────────────────────┘
                    │
                    ▼
        ┌─────────────────────┐
        │   后端 API 服务       │
        │   按区块返回建筑数据  │
        └─────────────────────┘
                    │
                    ▼
        ┌─────────────────────┐
        │   Godot 前端         │
        │   只加载附近区块      │
        │   卸载远处区块        │
        └─────────────────────┘
```

### 1.2 区块划分

```
巴黎 10km × 10km
    │
    ├── 50 × 50 = 2,500 个区块
    │
    ├── 每个区块 200m × 200m
    │
    └── 每个区块约 40-100 栋建筑
```

### 1.3 加载策略

```
玩家在位置 (x, y)
    │
    ├── 加载当前区块（200m×200m）
    ├── 加载相邻 4 个区块（预加载）
    │
    ├── 玩家移动到新区块
    │       │
    │       ├── 加载新相邻区块
    │       └── 卸载远处区块
    │
    └── 始终保持 ~5 个区块在内存中
```

### 1.4 性能预算

| 指标 | 数值 | 说明 |
|------|------|------|
| 同时加载建筑 | 200-500 栋 | 5 个区块 |
| 同时面数 | 3,000-6,000 | 每栋 12 面 |
| 内存占用 | 50-100 MB | 远低于浏览器限制 |
| 加载延迟 | < 1 秒 | 按需请求 |

### 1.5 数据格式

```json
// 每个区块的建筑数据
{
  "chunk_id": "48.8566_2.3522",
  "buildings": [
    {
      "id": "way/123456",
      "footprint": [[x1,y1], [x2,y2], ...],
      "height": 22.0,
      "type": "residential",
      "name": "15 Rue de Rivoli"
    }
  ],
  "streets": [
    {
      "name": "Rue de Rivoli",
      "width": 12.0,
      "points": [[x1,y1], [x2,y2], ...]
    }
  ]
}
```

### 1.6 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ 整个巴黎都可探索 | ❌ 需要后端 API 服务 |
| ✅ 内存占用低 | ❌ 需要网络请求 |
| ✅ Web 端可运行 | ❌ 离线不可用 |
| ✅ 建筑数据真实 | ❌ 开发复杂度高 |

## 二、方案 B：程序化生成 + 真实数据锚点

> **核心思路：** 用真实 OSM 数据作为"锚点"，其余区域用程序化规则填充。

### 2.1 架构

```
真实数据（OSM）           程序化生成
    │                       │
    ├── 地标建筑            ├── 普通住宅楼
    ├── 主要街道            ├── 小巷
    ├── 咖啡馆/餐厅         ├── 重复的 Haussmann 建筑
    └── POI 位置            └── 填充用建筑
    │                       │
    └───────────┬───────────┘
                ▼
        合并为完整场景
```

### 2.2 生成规则

```python
# 伪代码：程序化生成巴黎建筑

def generate_building(position, block_type):
    if block_type == "landmark":
        # 地标：用真实 OSM 数据
        return load_osm_building(position)
    
    elif block_type == "haussmann":
        # Haussmann 区：用规则生成
        height = random(18, 25)  # 6-7层
        width = random(8, 15)
        depth = random(10, 20)
        color = "#F5F0E8"  # 奶白色
        roof_color = "#4A4A4A"  # 灰色
        return create_box(width, height, depth, color, roof_color)
    
    elif block_type == "modern":
        # 现代区：用不同规则
        height = random(20, 50)
        return create_box(width, height, depth, "#CCCCCC", "#333333")
```

### 2.3 巴黎分区规则

| 区域 | 建筑风格 | 生成规则 |
|------|---------|---------|
| 1-4 区（市中心） | Haussmann | 6-7层，奶白外墙 |
| 5-6 区（左岸） | Haussmann + 大学 | 类似，略低 |
| 7 区（埃菲尔铁塔） | 混合 | 地标优先 |
| 8 区（香榭丽舍） | 商业 | 更宽的街道 |
| 13-14 区（南部） | 现代 | 更高的建筑 |
| 18-19 区（北部） | 混合 | 更密集 |

### 2.4 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ 不需要后端 API | ❌ 普通建筑不够真实 |
| ✅ 离线可用 | ❌ 需要编写生成规则 |
| ✅ 加载快 | ❌ 可能有重复感 |
| ✅ 整个城市都有 | ❌ 细节不如真实数据 |

## 三、方案 C：混合方案（推荐）

> **核心思路：** 真实数据做"骨架"，程序化做"血肉"，流式加载做"按需"。

### 3.1 三层架构

```
┌─────────────────────────────────────┐
│  Layer 1: 地标层（真实数据）          │
│  凯旋门、埃菲尔铁塔、卢浮宫等        │
│  约 50-100 个地标                    │
│  手动建模或高精度 OSM 数据            │
└─────────────────────────────────────┘
                    │
┌─────────────────────────────────────┐
│  Layer 2: 街区层（OSM 数据 + 简化）   │
│  主要街道、街区轮廓                  │
│  约 2,500 个区块                     │
│  每个区块按需流式加载                │
└─────────────────────────────────────┘
                    │
┌─────────────────────────────────────┐
│  Layer 3: 填充层（程序化生成）        │
│  普通建筑、小巷、庭院                │
│  用规则生成，不需要 OSM 数据          │
│  随时生成/销毁                       │
└─────────────────────────────────────┘
```

### 3.2 玩家体验

```
玩家在香榭丽舍大街（真实 OSM 数据）
    │
    ├── 看到凯旋门（地标，高精度模型）
    │
    ├── 走进旁边小巷（OSM 数据 + 简化建筑）
    │
    ├── 走进一家咖啡馆（标记为可进入）
    │       │
    │       └── 开始法语对话（核心体验）
    │
    └── 继续探索（流式加载新区域）
```

### 3.3 技术实现

| 层 | 数据来源 | 加载方式 | 面数/栋 |
|----|---------|---------|--------|
| 地标层 | 手动建模 / 高精度 OSM | 一次性加载 | 500-5,000 |
| 街区层 | OSM 数据 + 盒子简化 | 按区块流式加载 | 12-24 |
| 填充层 | 程序化规则 | 随时生成 | 6-12 |

### 3.4 优缺点

| 优点 | 缺点 |
|------|------|
| ✅ 地标真实还原 | ❌ 开发复杂度最高 |
| ✅ 街区布局真实 | ❌ 需要后端服务 |
| ✅ 普通建筑可接受 | ❌ 填充层可能有重复感 |
| ✅ 性能可控 | ❌ 需要大量测试 |
| ✅ 整个巴黎可探索 | |

## 四、后端 API 设计（方案 A/C）

### 4.1 API 端点

```
GET /api/chunks/{lat}_{lng}
→ 返回该区块的建筑+街道数据

GET /api/landmarks
→ 返回所有地标位置和模型路径

GET /api/buildings/nearby?lat=&lng=&radius=200
→ 返回玩家附近的建筑（备用方案）
```

### 4.2 数据预处理

```
1. 下载整个巴黎 OSM 数据（~500MB）
2. 用 Python 脚本：
   - 按 200m×200m 切割成区块
   - 每个区块提取建筑+街道
   - 简化建筑轮廓为矩形
   - 计算建筑高度
3. 保存为 JSON 文件（每个区块一个文件）
4. 部署到 CDN 或静态服务器
```

### 4.3 Godot 侧加载

```gdscript
# 流式加载区块
func load_chunk(chunk_id: String):
    var url = "https://api.linguaverse.app/chunks/" + chunk_id
    http_request.request(url)

func _on_chunk_loaded(chunk_id: String, data: Dictionary):
    for building in data.buildings:
        var mesh = create_box_mesh(building)
        var instance = MeshInstance3D.new()
        instance.mesh = mesh
        add_child(instance)
    
    loaded_chunks[chunk_id] = true

func unload_distant_chunks(player_pos: Vector3):
    for chunk_id in loaded_chunks:
        var chunk_pos = get_chunk_position(chunk_id)
        if player_pos.distance_to(chunk_pos) > 400:
            remove_chunk(chunk_id)
            loaded_chunks.erase(chunk_id)
```

## 七、结论

| 问题 | 答案 |
|------|------|
| 整个巴黎能做吗？ | **能，但需要流式加载架构** |
| 性能够吗？ | **够。** 只加载附近 200m 范围 |
| 需要后端吗？ | **需要。** 负责返回区块数据 |
| 建筑真实吗？ | **地标真实，普通建筑用规则生成** |
| 工作量多大？ | **V1 小街区 3-4 周，整个巴黎 2-3 个月** |
